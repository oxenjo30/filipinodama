## 2026-07-22 - Login keyboard stuck up = a view-backed EditText with no imeOptions/editor-action

- Symptom: on the mobile login screen, the password vault autofills, user presses Enter, and the soft keyboard never hides (covers the bottom nav).
- Root cause: the auth fields are NOT the Compose AuthTextField — they're a native EditText inside AndroidView (AuthAutofillField.kt, used so the PLATFORM vault handles fill + "Save password?"). It set inputType but NO `imeOptions` and NO `setOnEditorActionListener`, so Enter was a no-op — nothing dismissed the IME.
- Fix: email/login → `IME_ACTION_NEXT` (focusSearch(FOCUS_DOWN)); password → `IME_ACTION_DONE` → InputMethodManager.hideSoftInputFromWindow + clearFocus + submit callback.
- GOTCHA that would silently reintroduce the bug: `EditText.setInputType(...)` RESETS imeOptions to default. AuthAutofillField reassigns inputType in its AndroidView `update` block on every recompose (password show/hide toggle), so imeOptions MUST be re-applied right after that reassignment.
- Rule: for any view-backed (AndroidView/EditText) text field, IME dismissal is NOT automatic — set both `imeOptions` AND a `setOnEditorActionListener`, and re-apply imeOptions after ANY `setInputType`. Note there are TWO auth field widgets here: Compose `AuthTextField` and native `AuthAutofillField` (login/signup use the native one for vault SAVE) — fix the right one.

## 2026-07-22 - "You're offline — reconnecting…" flash on app open = Android's VALIDATED lag, not the app

- Symptom: owner saw the red "You're offline — reconnecting…" banner for ~1-5s every time the app opened, on a good connection.
- Root cause: ConnectivityObserver (correctly) requires `NET_CAPABILITY_VALIDATED`, not just `NET_CAPABILITY_INTERNET` — this guards against captive-portal Wi-Fi (link up, no real internet). But on a cold open/resume Android hasn't finished its captive-portal probe, so it momentarily reports "not validated" → false offline → banner flash. There was NO app-side reconnect timer; the banner tracked Android's signal 1:1.
- Fix: an ASYMMETRIC debounce (`Flow.debounceOffline` via `transformLatest`): offline emits only after ~2.5s continuous offline (swallows the on-open blip); online emits IMMEDIATELY (never delay the good-news edge, so a real outage still clears instantly). Do NOT weaken detection to plain INTERNET — that reintroduces the captive-portal false-online.
- Self-correction during the fix: my first attempt put `delay(graceMs)` inside a plain `.collect{}`. That's WRONG — collect is sequential, so the delay blocks the next event; an online arriving mid-grace wouldn't be seen until the delay finished, defeating the instant-online goal. `transformLatest` is the right primitive: a new upstream value cancels the previous value's suspending block, so online mid-grace cancels the pending `emit(false)`.
- Rule:
  1. A "reconnecting…"/offline flash ONLY on open (not during use) points at the OS validation window, not at app socket/reconnect logic — check the connectivity SIGNAL (VALIDATED vs INTERNET) before touching reconnect code.
  2. For asymmetric edge debouncing (delay one direction, pass the other instantly) use `transformLatest { if (fast) emit else { delay; emit } }`, never `delay` inside `collect` (which blocks the stream).
  3. `transformLatest` is `@ExperimentalCoroutinesApi` in kotlinx-coroutines 1.9.0 → needs `@OptIn(ExperimentalCoroutinesApi::class)` or it won't compile.

## 2026-07-22 - A "vanished" session was a worktree session logged under a DIFFERENTLY-CASED project dir

- Situation: owner reported "last night's session is gone, I can't continue." It didn't appear in the main checkout's resume list because it had run INSIDE a git worktree, and Claude Code stores each worktree's transcripts under its OWN project dir keyed by the worktree path — e.g. `~/.claude/projects/D--AI-Projects-FilipinoDama--claude-worktrees-bump-v46/` (note the UPPERCASE `D--`), NOT the main repo's `d--AI-Projects-FilipinoDama/` (lowercase). Searching only the lowercase dir missed it entirely.
- How it was found: `git reflog` + `git worktree list` in the main checkout revealed a scratchpad worktree path containing a session UUID; `find ~/.claude/projects -iname '<uuid>*'` (case-insensitive) located the .jsonl. To enumerate ALL sessions for a repo you must glob every case/worktree variant: `ls ~/.claude/projects/ | grep -i filipino`, then sort each dir's newest .jsonl by the LAST internal `"timestamp"` (on-disk mtime lies — the harness re-touches old files to 07:34-ish when a new session boots, so mtime ≠ last real activity).
- Rule:
  1. To find a "lost" session, search `~/.claude/projects/` case-INSENSITIVELY across every `<repo>` and `<repo>--claude-worktrees-<name>` variant, and rank by the last in-file `"timestamp"`, never by file mtime.
  2. A worktree session resumes from the WORKTREE folder (`cd <worktree> && claude --resume <uuid>`), not the main checkout — that's why it's missing from the main repo's picker.
  3. `git reflog` + `git worktree list` + the scratchpad path (which embeds the session UUID) are the bridge from "which git state was mid-flight" to "which transcript to reopen."

## 2026-07-21 - Flaky CI: an async settle's ledger write raced truncateAll (P2003) — wait for the real event, don't setTimeout; and beware a rogue local Redis on 6379

- Symptom: PR CI failed in `truncateAll` (helpers.ts) with `P2003` on `prisma.user.deleteMany` → `LedgerEntry_userId_fkey`, while the IDENTICAL code passed on `main` and on the prior PR. Classic timing-sensitive flake, NOT caused by the PR's actual change (an Android-only edit can't fail a server test).
- Root cause: `matches-live-rooms.test.ts` resigned a match then `await setTimeout(100)`. Resigning runs `settleMatch`, which INSERTS a LedgerEntry (FK→User) BEFORE it broadcasts `EV.matchEnded`. Under load the write outran 100ms and landed AFTER `afterEach`'s truncateAll → the follow-up user deleteMany hit the fresh FK row. Adding the tournament-sim suite (~40s load) shifted timing enough to surface the latent race.
- Fix (two layers): (1) wait for the real `EV.matchEnded` (settle applies the ledger BEFORE emitting it, so the event proves the write landed) instead of a blind sleep; (2) harden `truncateAll` — on a P2003 from any late async FK insert, re-TRUNCATE the child tables and retry (bounded 3x), so the whole class of late-write race can't red-light CI.
- Rule:
  1. Never gate an async DB side effect on a fixed `setTimeout` in a test — wait for the actual completion signal (the broadcast/event/row-state). Fixed sleeps flake the instant load shifts.
  2. When a test fails but the same commit is green elsewhere, suspect a shared-DB/Redis timing race, not the diff. Reproduce by running the suspect file together with a heavy suite (adds load).
  3. LOCAL GOTCHA: two processes can BOTH listen on 6379 — the docker-compose `redis:7` proxy AND a stray native `redis-server`. Windows may route `redis://localhost:6379` to the OLD native one, which lacks `UNLINK` (helpers' flushRealtimeKeys uses it) → `ERR unknown command 'unlink'`. That's a local env collision, NOT a code bug. Run a clean `docker run -d --name fd-test-redis -p 16399:6379 redis:7-alpine` and point `REDIS_URL=redis://localhost:16399` at it. CI is unaffected (compose-only).

## 2026-07-21 - Running a NEW test that needs the full toolchain from a fresh worktree: run in the parent checkout, keep the authoritative copy in the worktree

## 2026-07-19 - A fresh git worktree has NO installed node_modules → tsc can't typecheck there

## 2026-07-18 - A "feature not working" report was a missing prod CONFIG ROW, not a code bug

- Symptom: Owner reported the in-app "update available" nudge never appears despite a newer version existing. Instinct is to debug the client code.

## 2026-07-17 - "compileDebugKotlin clean" missed errors that only compileReleaseKotlin caught

- Mistake: Verified Android changes with `:app:compileDebugKotlin` (exit 0) and called them done. The RELEASE bundle build then failed at `:app:compileReleaseKotlin` on a missing import (`navigationBarsPadding`) and a duplicate import (`Arrangement`) — errors the debug compile did NOT surface. The green debug compile was falsely reassuring for exactly the files that were broken.

  2. When you COPY a file from another worktree/branch into this one, its imports are only valid if that file's deps also exist here — recompile it specifically (or clean-compile), don't trust an incremental debug pass.
  3. Watch for duplicate imports when multiple agents edit the same file's import block — one adds an import another already added. The release compiler treats an ambiguous/duplicate import as an error.

## 2026-07-17 - Shipped pull-to-refresh that silently did nothing on loading/empty/error states

- Mistake: Wired `PullToRefreshBox` (material3 1.3.0) on ~18 screens by wrapping each screen's `when {}` content. It compiled and worked ON A POPULATED LIST, so I called it done — but on the LOADING, ERROR, and EMPTY branches (a bare `Box`, or a `Column` with `fillMaxSize()` but NO `verticalScroll`) the pull gesture did nothing: no spinner, no refetch. The empty state is the FIRST thing a user sees on a fresh screen, so it read as "pull-to-refresh is broken."
